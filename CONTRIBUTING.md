# Contributing

Thanks for taking the time to contribute. Issues and pull requests are both welcome.

## Requirements

- JDK 21
- Android SDK with platform 37
- Android Studio with AGP 9 support

## Build and test

```bash
./gradlew :danmaku:assembleDebug
./gradlew :danmaku:testDebugUnitTest
./gradlew :app:assembleDebug
```

`:danmaku` holds the published code, `:app` is a sample that consumes it.

On Windows, git does not record the executable bit. After adding or replacing `gradlew`, run
`git update-index --chmod=+x gradlew` before committing: CI runs the wrapper on Linux, where a
non-executable `gradlew` fails the build.

`DanmakuOverlay` drives a frame loop that never ends, so Compose never reports an idle state while the layer is
composed. A test built on `createComposeRule` - instrumented or Robolectric - times out rather than fails,
whether or not the overlay is what is under test. An attempt to cover the selection gesture this way timed out
at 54 to 121 seconds per test, and neither `mainClock.autoAdvance = false` nor
`withInfiniteAnimationFrameNanos` helped. Logic that does not need composition therefore lives outside the
composable, in `xyz.larkzhh.danmaku.engine`.

Dependencies resolve from Google and Maven Central.

## Code style

- The build runs in Kotlin explicit API mode, so a public declaration needs an explicit visibility modifier
  and an explicit return type. The compiler enforces this, not review.
- Public API is documented with English KDoc, including `@param` and `@property` for everything that is
  not obvious.
- Inline comments explain why something is done, not what the code already says.
- No commented out code and no `TODO` without a linked issue.
- Lane allocation, placement and hit testing stay pure and live in `xyz.larkzhh.danmaku.engine`, so they
  can be covered on the JVM without a device. New layout rules need unit tests there.

## AI-generated content

A report - a document whose claims are measured figures rather than behaviour a reader can check by running
the code - carries a marker in a blockquote before its first section:

> **Generated by an AI assistant.** The figures are measurements taken on the device named above, not
> estimates. The commands under Reproducing regenerate them.

The marker states how the claims were checked. "Generated" on its own says nothing about whether they are
true, and the claims are what a reader has to rely on.

Nothing else carries a marker. `README.md` and the other documentation describe behaviour the code exhibits,
which a reader checks by using the library, and code and tests are checked by the build and the test suite.
Both are stronger evidence than a label.

## Commits

The project uses [Conventional Commits](https://www.conventionalcommits.org/): `feat(scope): ...`,
`fix(scope): ...`, `test(scope): ...`, `docs: ...`.

One change, one commit. A feature carries its own tests and its own documentation, so they go in the same
commit. Splitting them into `feat`, `test` and `docs` commits buries the change in bookkeeping. Releases are
the exception: they get a `chore(release): x.y.z` of their own, because the tag points at that commit.

## Pull requests

1. Keep the change focused, one topic per pull request.
2. Add or update tests when behaviour changes.
3. Run `./gradlew :danmaku:testDebugUnitTest` and `./gradlew :app:assembleDebug` before opening the pull
   request.
4. Update `CHANGELOG.md` under `Unreleased`.
